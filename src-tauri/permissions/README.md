# App-command permissions (wayfinder/v1.2.0/D06)

This directory holds the ACL definitions that gate the keyring commands.
The shell must list the commands in the app manifest for the gate to
engage; without that, Tauri 2 treats application commands as allowed by
default.

## How the gate works

1. `build.rs` passes an `AppManifest` with the four commands to
   `tauri_build::Attributes` (see the wiring note in
   `src/keyring.rs`). tauri-build then:
   - regenerates the `autogenerated/*.toml` files below (they are
     committed because the generator output is deterministic and
     `write_if_changed` keeps them in sync),
   - registers an app ACL manifest, which removes the four commands from
     the default-allowed set.
2. The IPC layer rejects any invocation of a manifest-gated command that
   no capability grants (`tauri` 2.11.5, `src/webview/mod.rs`
   `on_message`): the denial happens before the Rust handler runs.
3. `capabilities/default.json` grants `allow-keyring-set`,
   `allow-keyring-get`, `allow-keyring-delete`, `allow-keyring-tier` to
   the `main` window only. Remote pages have no capability, so any
   keyring invoke from a persea server page fails with
   `keyring_set not allowed on window ...` (and independently of this
   manifest, Tauri rejects every custom command invoked from a remote
   origin unless a `remote` capability grants it).

## Files

- `autogenerated/keyring_set.toml`, `keyring_get.toml`,
  `keyring_delete.toml`, `keyring_tier.toml`: machine-generated
  `allow-*` / `deny-*` permissions, one pair per command. Do not edit by
  hand; the build rewrites them.
- The directory is scanned by tauri-build's default
  `permissions/**/*` glob, so no extra `permissions_path_pattern` is
  needed in `build.rs`.
